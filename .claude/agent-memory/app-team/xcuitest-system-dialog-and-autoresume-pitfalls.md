PhotoTimerでバックグラウンド対応(ローカル通知の許可ダイアログ)と「前回状態の自動復元」機能を追加した際、
XCUITestが原因不明で長時間ハング/失敗する事象が発生し、切り分けに大きく時間を要した。他のiPhoneアプリの
UIテストでも同じ形の機能を足す時に再発しうるため記録する。

**落とし穴1: 新規追加したOS標準ダイアログをテストが処理しない**
機能追加(例: 通知許可・位置情報許可など)で新たにOS標準の許可ダイアログが出るようになると、
それを操作しないままの既存テストが「隠れた要素を待ち続けて延々とタイムアウトする」形で止まる。
写真アクセス許可のような「最初から想定していたダイアログ」だけでなく、後から機能追加で
増えるダイアログにも同様の対策が要る。
**対策**: (1) `setUpWithError()`で`addUIInterruptionMonitor(withDescription:handler:)`を登録し、
該当ボタン(例:"許可")があれば自動タップする。(2)保険として、ダイアログが出うる操作の直後に
`springboard.buttons["許可"]`を数秒だけポーリングするヘルパーも用意する(interruption monitorは
「次にアプリ側で何らかの操作が起きるまで検知が遅れる」ことがあるため、二重に構える)。

**落とし穴2: 「前回の状態を自動復元する」機能とテストの連続実行が衝突する**
アプリ終了時にも状態を復元する機能(例:バックグラウンド中に強制終了されたタイマーを次回起動時に
自動再開する)を追加すると、**テストが失敗して後始末(閉じる操作)をしないまま終わった場合、
その状態が残り続け、次のテスト(次のapp.launch())で自動的に復元されてしまう**。
これによりホーム画面から始まるはずのテストが古い画面のまま動かなくなり、原因が「今回追加した機能」
ではなく「別の何か」に見えて調査が長引く。
**対策**: (1)アプリ側:復元の判定はプロセス起動ごとに1回だけに制限するフラグを持つ
(SwiftUIなら`@State`のワンショットガード)。(2)テスト側:各テストの冒頭(許可確認のすぐ後)で
「ホーム画面の目印が無ければ、前回の画面とみなして閉じる」共通処理を必ず通す。
(3)自分で調査中にテストプロセスを強制終了(kill)すると、この後始末が走らないまま状態が残るため、
不用意なkillは避け、可能な限りテストを完走させるか、killした場合はアプリを一度アンインストールしてから
次のテストに臨む。

**関連の環境固有事象(未解決・要実機再確認)**: 上記2つを解消した後も、この開発機の特定のシミュレータで
「写真アクセス許可の直後にPHImageManager.requestImageが全件PHPhotosErrorDomain Code=3303
("Image request failed")で失敗する」事象が残った。isNetworkAccessAllowed/deliveryModeの変更や
シミュレータ再起動でも解消せず、実機では同条件が問題なく動作した(候補6044件の準備0.18秒・
1枚目0.26秒)ため、シミュレータ環境固有の問題と判断した。他のプロジェクトで同種の「写真許可直後だけ
全件失敗する」事象に遭遇した場合、コードを疑う前にシミュレータの作り直し(アンインストールでなく
シミュレータ自体の再作成)や実機での再現確認を先に行うと切り分けが早い。
